# 验证证据与发布交接

用于复现、测试记录、提交前核验及 PR 状态解释。以下是工作记录结构，不是替代仓库官方 PR 模板的固定模板。

## 目标仓库适配清单

开始新仓库的贡献时，在现有工作记录中建立简短的项目事实卡；继续同一仓库时刷新会变化的项目，不重复索取已知信息。以下是需要确认的事实，不是要求项目必须具备这些文件或机制。

| 项目项 | 从哪里确认，以及不能继承什么 |
| --- | --- |
| 仓库身份 | 用户指定的完整仓库地址、托管平台、工作目录、上游与 fork；不能因当前目录仍是旧项目就选错目标 |
| 修复目标 | 项目要求的目标分支、版本与基线 SHA；不默认 main，也不把最新主线结果代替维护版本结果 |
| 接受条件 | CONTRIBUTING、适用 AGENTS、安全政策、功能讨论流程、AI 政策；必要时查看近期同类 PR 的维护者意见 |
| 工具链 | 项目配置、锁文件、CI、文档中的语言/运行时版本、依赖管理和安装方式；不默认 Python、Node、uv 或 pnpm |
| 验证范围 | 对应模块、完整离线套件、必需质量检查及相关平台/集成条件；记录无法本地执行的项目，不静默忽略 |
| 文案格式 | 当前 issue/PR 模板、项目语言、变更日志或迁移说明要求；不存在的栏目不假称必填 |
| 身份与授权 | 当前账号、fork 写权限、提交身份、项目要求的 CLA/DCO；其他仓库的登录/协议状态不能替代核验，也不代用户签署或声明 |
| 交接位置 | 当前仓库的本地证据目录、网页目标、本人审阅情况；沿用用户自己最终提交的约定，不沿用旧项目发布授权 |

同一托管平台上的身份或公开 issue 编号也必须与仓库全名一起核对。其他平台的变更请求按其真实表单和关联机制处理，不保证 GitHub 的 `Fixes`、Draft 或审阅按钮在那里有相同含义。

## 按项目类型选择验证

以下是条件性提示，按本次真实改动选择，不是每次全部执行的清单。缺陷修复仍必须满足先红后绿和当前项目的必需检查，不能因换了语言而降低门槛。

| 实际改动 | 额外关注的证据 |
| --- | --- |
| 库、SDK 或 CLI | 公开 API/命令入口、返回值/异常/退出码、输入输出兼容性；不只测内部帮助函数 |
| 服务或数据层 | 真实处理入口、数据落库与事务边界、重试/并发、权限和错误返回；区分 mock、离线集成与实际部署 |
| Web 或其他 UI | 可操作的实际界面、状态转换和保存结果；有视觉变化或模板要求时附实际截图，视口/设备范围按目标平台确定 |
| 多平台或底层组件 | 受影响操作系统、架构、资源生命周期；未在目标平台运行时明确缺口，不把本机模拟等同原生验证 |
| Agent 或模型集成 | 工具与状态边界、失败路径、可重现的离线替身；若声明模型效果改善，另需固定评估数据和基线，不能用普通单测数量代替 |

若用户明确选择性能、功能或文档贡献，改用该类型的证据：性能用可重复的同环境基准及正确性检查；功能先确认需求/设计接受度并做验收与兼容性测试；文档核对真实行为、示例和文档构建。不能把这些贡献包装成已复现 bug，或为了形式强造失败回归；查重、实际价值、诚实验证和本人最终提交仍适用。

## 最小审阅包

优先沿用项目已有 `work/`、`outputs/` 或其他约定。没有约定时，可在本地工作目录创建一个以问题命名的目录，包含：

- `review.md`：中文解释，真实操作、根因、修改范围、非目标、审阅所需文件。
- `validation.md`：基线和修复 SHA、环境、完整命令、结果和日志路径。
- `issue.md` / `pr.md`：仅保存当前阶段需要的官方模板文案。
- 实际需要的截图和日志；避免重复备份、私人数据以及上传完整环境。

不得把历史时间戳、测试计数或示例结果复制成下一次执行的结果。

## 候选证据卡

| 字段 | 需要的事实 |
| --- | --- |
| 来源 | 已有 issue、用户报告或自行代码审查 |
| 相关记录与审查范围 | 本轮简短查过的已有记录、检查的真实流程/调用链、跳过原因；不要求穷尽 issue，但不能把有限搜索说成“仓库没有问题” |
| 真实入口 | 用户操作、请求或工具调用，从哪里进入 |
| 当前版本 | 上游分支、SHA、检查日期 |
| 实际与预期 | 可观察差异；预期来自什么产品约定 |
| 用户影响与价值 | 丢数据、错误调度、缺图等后果；触发条件为何现实，行为变化与维护成本是否合理；不要虚构发生频率 |
| 对照与反证 | 正常场景是否保持正确；是否排除了刻意设计、已修复、调用方已处理和环境/夹具问题；说明故障注入模拟了什么 |
| 查重 | 时间、查询词、查询范围、最相近 PR 链接、实际不同点、接手人或拒绝理由；记录未完成的检索 |
| 结论 | 继续、等待复现/设计确认、已有修复、跳过 |

对自行发现的问题，必须同时证明“现在存在”和“值得改变”。某段代码看起来不理想不自动构成 issue。自主发现是选题方式，不是必须创建新 issue 的指标；查到同题现有报告就关联它，不重复报告。

## 阶段门槛

以下以缺陷修复为默认，列出建议进入下一阶段的条件，不是代用户发布的授权。每项只记“有证据满足”“待验证/待确认”或“不满足”，并链接实际证据。非缺陷贡献的真实性以已确认需求、实际性能基线或文档与行为的差异为依据，不能套写“当前 bug 已复现”。

| 检查项 | 满足所需证据 | 不满足或未知时 |
| --- | --- | --- |
| 真实性 | 当前上游可复现，真实入口可达，排除夹具与环境原因 | 不作为已确认 bug 发布，继续调查 |
| 价值与合理性 | 明确用户后果、预期依据及合理的修复范围 | 不把个人偏好包装成 bug；必要时先讨论 |
| 查重 | 检查相关 open/closed/merged issue/PR、认领情况和最新实现，比较最近似 diff；无需遍历整个 issue 列表 | 同题已有 issue 就复用；有同范围修复/明确接手人则停止竞争修复；关键检索缺失则暂不建议发布 |
| 修复与验证 | 缺陷修复的同一回归先红后绿，相关边界和项目必需检查完成，失败/跳过有解释；非缺陷贡献使用上文对应的验收证据 | 核心未跑、新增失败或未解释失败则待补验证，不能称已就绪 |
| 本人审阅与文案 | 用户确认当前最终差异；官方模板、真实关联及 AI 披露准确 | 保持声明未勾选，说明待审阅部分，不虚构已理解或负责 |

issue 的真实性、价值和查重满足后，即可为用户准备报告；不要求先完成修复或全部修复测试。报告按当前官方模板包含版本、最小复现、预期/实际、影响和证据。

建议用户提交可供审阅的 PR 前，还需满足修复验证及项目要求的本人审阅。已证实的上游原有失败、可选集成跳过可以如实披露，但不能冒充全部通过；未解释失败或缺少本次核心证据不能放行。待审阅或受阻时可保存本地草稿，这不等于获准创建 GitHub Draft PR。

## 测试账本

每一项保留工作目录、命令、SHA、环境、通过/失败/跳过数、退出状态及日志。环境配置可记录无敏感值的变量名，不能保存真实密钥。

另外记录本次修复的用例表：`场景/输入或操作 -> 预期 -> 基线实际结果 -> 修复后结果 -> 测试文件或日志`。至少说明目标失败路径、正常对照及按风险选择的边界；列明 mock 的范围，不能用预设正确结果的 mock 证明被替代的生产逻辑正确。测试数据只需足以证明行为，不追求堆样本数量。

| 阶段 | 证据要求 |
| --- | --- |
| 修复前 | 未修改生产代码，新增回归测试因目标行为失败 |
| 修复后 | 相同测试通过，不能改断言绕过原问题 |
| 模块验证 | 同模块及主要消费者的相关测试 |
| 项目检查 | 项目要求的完整离线测试、lint、format、类型、构建等 |
| UI 验证 | 真实页面与浏览器断言，不只检查返回字符串或截图存在 |
| 最终差异 | 未混入日志、缓存和无关改动；必要锁文件变更有依据；源码与已验证版本一致 |

遇到异常时：

- `skipped`：读取跳过原因，判断是不是覆盖本次核心路径。可选在线集成没凭据与核心回归被跳过不能混为一谈。
- 端口权限、磁盘满、代理、依赖下载失败：记录为环境阻塞；修复环境后重跑，不能说产品测试通过或产品有 bug。
- 怀疑 flaky：保留失败输出，做基线及完整套件对照；未确认根因就写未确认。单次重跑通过不能抹去前次失败。
- 基线上也失败：记录具体相同失败与证据，再说明是否和本次差异相关。不要凭文件名判断无关。
- 基线更新：结果绑定原 SHA。仅当变更与目标完全无关且源码/环境未变，才明确引用已有结果；不能把未执行的检查写成新跑的。
- 运行被中断或进程仍在执行：报告未完成，不能推算通过数；结束前收集需要的进程结果并清理自己启动的临时服务。

## 按风险选择边界

不要求每个 PR 都执行以下全部场景；按实际改动选。

- 文件发布：二方和多方竞争、跨请求已存在文件、原文件字节保持、转换伴随文件、错误传播、清理异常、符号链接替换、平台能力差异。
- 转义/编码：原始数据来源、上游已解码内容、重复执行/重试、百分号和 Unicode、URL 查询与片段、正常外链、既有 sanitizer。
- 前端状态：默认值、原始旧值、切换后再修改、同文本不同对象、实际保存请求、窄屏入口、真实渲染器缓存。
- 权限与安全：用项目支持的测试入口验证，不公开真实凭据；模拟授权不能写成真实部署认证通过。

## PR 文案核验

使用当前仓库模板，至少确保维护者能快速找到问题、修复后的行为、范围、验证和关联 issue。若模板含 Surface area 等分类，只勾选实际影响的项；未涉及区域留空不是“未完成任务”。没有此类栏目时不要照搬其他项目的勾选表。

确认该仓库接受对应 AI 参与方式后，披露按实际参与和目标模板调整，例如确实都做过这些活动时才写：

```text
Tool(s) used: Codex
How you used it: Assisted with reproducing the issue, implementing the focused fix
and regression tests, running local validation, and drafting the PR description.
```

如果实际生成了代码，不得描述成仅润色文字。只有用户对当前差异作出真实审阅确认后，才能代填“已阅读理解并负责”；旧 PR 的确认不适用于新的 PR，新增实质差异也不自动继承确认。

截图标题说明数据来源、入口、前后版本和视口；合成报告/模拟 API 要注明。报告为了覆盖不同路径而重复引用同一图片时明确解释，不制造影响程度夸张的印象。

## 用户自己提交时

当前约定是用户自己点击最终按钮，不只是“用户确认后代理点击”。准备文案、勾选真实声明、上传获准截图、代码提交或推送，均不自动授权创建 issue/PR 或 Ready for review。后续只有明确变更本次最终操作人，才能改变这个约定。

1. 核对页面账号、仓库、base/head、标题和真实差异，保留用户最近手动填写的内容。
2. issue 尚未创建时不捏造编号。用户创建后读取真实页面，再在 PR 中使用对应链接。
3. `Fixes #N` 仅用于完整解决；部分修复用 `Related to #N` 并说明剩余范围。
4. 按照实际审阅情况保留责任声明状态，明确未完成项；不要把所有框统一勾选。
5. 明确当前按钮是创建普通 PR 还是草稿；告诉用户最后需点什么并停下，不用快捷键、脚本、API 或 CLI 替用户触发。切换草稿状态不等于修改正文。
6. 发布后读取真实 URL 确认结果，不根据“按钮按了”推定发布成功。若有附件工具，关联已创建或正在继续的 PR。

用户误创建草稿时通常无需重建：审阅就绪后可使用 Ready for review；过期的正文草稿说明和本人审阅声明需分别处理。具体界面和权限以当时真实页面为准。

## 状态解释表

| 看到的状态 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- |
| 本地测试通过 | 在记录的代码、环境、检查范围下通过 | GitHub CI、维护者批准或合并 |
| CLA signed | 当前检查认定提交者协议满足 | 代码已审阅或其他项目也已签署 |
| Awaiting workflow approval | 工作流等维护者授权运行 | 测试已经失败 |
| Failure / 红叉通知 | 对应工作流运行报告失败；要读运行注释、jobs 和失败步骤 | 当前提交必然有代码错误，或测试必然执行过 |
| Required approval expired | 核实注释后，可说明该次运行未及时获批而过期 | 测试断言失败，或其他红叉也必然是同一原因 |
| Skipped checks | 某些 job 没执行，需看条件和必需性 | 所有跳过都无害或整个测试没运行 |
| Bot success / no new issues | 机器人运行完成或没提出新问题 | 正确性保证、正式人工批准 |
| Review required | 还缺满足分支规则的批准 | 一定存在代码错误或维护者拒绝 |
| Out-of-date, no conflicts | 落后主分支，但当前可干净合并 | 必须重提 PR 或代码已有冲突 |
| Draft | 仍标为工作中，不能合并 | 无人能看代码或发表评论 |
| Merged | 该 PR 的合并操作完成 | 所有部署/发布都已更新 |
| Closed, not merged | 该 PR 关闭而未直接合并 | 其代码绝未通过另一 PR 被采用 |

查看状态时保留仓库全名，同一编号在不同仓库不是同一 PR。引用关系是有人在内容或提交中链接，不是 GitHub 自动识别相似 bug。

CI 结论绑定提交 SHA、工作流和 run attempt，先确定通知属于旧提交还是当前 head，再核对该版本最近相关运行。重跑成功不抹去首次失败；需要解释其原因及是否仍需处理。只抽查一个过期审批运行时，不把原因推广到所有红叉；同样，不能因部分流程成功就宣称所有 CI 通过。合并状态与检查状态分别报告，不擅自批准、重跑或修改工作流。

## 本地验收演练

校验 skill 或复查执行方案时，用这些情景检查决策，不实际发布测试 issue：

- 用户要求找新贡献，近期相关 issue 多已有人接手：完成简短背景/查重后，主动检查一个真实流程并做最小复现；不能停在“没有可领 issue”，也不无限扫列表。
- 自主发现的问题已由别人报告，但无人修复且当前仍可复现：复用真实 issue，准备修复 PR；不为了满足自主发现偏好另建同题 issue。
- 自主发现一个代码异味，但正常入口不可达或预期只是个人偏好：不准备 bug issue，继续调查或换流程，不先做补丁再找理由。
- 回归已通过，但最终查重发现同范围 PR 正在修复：停止竞争提交，记录为何跳过。
- 搜索不可用或最接近 PR 的 diff 没有读到：写查重未完成，不凭标题断定没有重复。
- 已有 issue 很旧，或自行构造了生产入口无法产生的输入：重新检查当前上游和可达性，不能据此直接宣称真实 bug。
- 观察到改任务名会改变调度时间，但语义不明确：先确认产品预期，不宣称仅凭测试就证明是 bug。
- 全量测试被端口权限挡住，少量单测通过：不能写全量通过，处理权限或清楚交接阻塞。
- 大量测试通过，但本次核心回归被跳过：仍是待补验证，不能靠总数宣布就绪。
- 用户只说“我看懂了”，没有指定提交：不据此点击 Create 或 Ready for review。
- 用户说“帮我写 PR”或“检查完没问题就提交”，但仍约定本人最后点击：完成准备并交接，不自行创建普通或草稿 PR。
- 用户发布了 issue，但 PR 还没发：核验真实编号并补关联，最终点击仍按既有边界交接。
- 机器人提示重复解码：追踪采集到存储的完整链路，而不是再添加一层字符串替换。
- 出现新的修复提交：重新判断旧审阅与测试覆盖范围，不自动沿用旧勾选和旧结果。
- 用户问旧 CI 红叉，而当前 head 已通过检查并合并：对照 SHA 和运行注释解释旧运行，不能凭红叉让用户重新改代码，也不未经核实声称红叉全是审批过期。
- 用户切换到另一仓库，目标分支是 develop 且使用不同测试工具：重新建立项目事实卡，不复用旧仓库路径、main 假设或测试命令。
- 新项目没有 PR 模板或网页 UI：提供精简贡献说明和实际 API/CLI 证据，不强塞旧项目的分类框或截图要求。
- 目标仓库禁止 AI 生成补丁：停止这种实现方式并报告约束，不改成“仅文案润色”来绕过。
