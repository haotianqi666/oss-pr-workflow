# 我们实际做过的贡献复盘

这里记录截至 2026-10-13 的工作经历，不是实时 PR 看板。来源是当前会话中用户提供的 GitHub 页面和项目工作记录；没有为了写本 skill 重新查询每个 PR。需要回答“现在怎么样”时重新读取 GitHub。测试数量属于当时版本，不可照抄到未来贡献。

这些案例集中于曾实际参与的少数仓库，不限定本 skill 的适用项目。复用的是验证和协作经验，不是具体项目的代码方案、工具链、表单、分支或操作授权；跨仓库先按主流程建立目标项目事实。

## #6308：Markdown 伴随文件的大小写不一致

链接：[bytedance/deer-flow#6308](https://github.com/bytedance/deer-flow/pull/6308)。历史记录已确认合并。

- 原问题：注册阶段接受 `report.MD`，查找阶段却只接受小写 `.md`。文件能登记，之后解析、列出伴随文件或提取大纲时找不到。
- 做法：让查找的后缀判断与注册规则一致，补一条贯穿注册与使用的回归测试，再运行上传与大纲相关检查。
- 经验：少量生产代码也可以解决真实一致性问题。含金量来自用户影响和闭环证据，不来自改动行数。
- 协作：CLA 和提交邮箱关联曾需处理；CLA 通过与 review 通过是两件事。历史机器人提醒可能落后于当前检查，应先核验再解释。

## #6466：大小写不敏感文件系统覆盖附件

链接：[bytedance/deer-flow#6466](https://github.com/bytedance/deer-flow/pull/6466)。历史记录已确认合并；关联更大的上传问题 #3750。

- 原问题：名称分配把 `Report.txt` 和 `report.txt` 当成不同文件，但本机文件系统把它们视为同一路径，第二次写入可能覆盖第一次内容。
- 做法：在分配唯一名称时用 `casefold()` 比较已有名称和后缀候选，并在上传入口验证两个附件内容都保留。
- 评审补充：维护者指出同一批附件的测试不能替代跨两次请求的测试。截图时间线显示后来出现补充测试提交，不能把“用户没手写补测”等同于“仓库没有补测”。具体作者归属以提交元数据为准。
- 经验：帮助函数测试、真实入口测试、跨请求场景各自覆盖不同风险。这个 PR 只解决大小写冲突，不应通过 `Fixes` 关闭整个并发上传问题。

## #6749：切换到自定义 cron 悄悄改变计划

链接：[bytedance/deer-flow#6749](https://github.com/bytedance/deer-flow/pull/6749)，对应 [issue #6748](https://github.com/bytedance/deer-flow/issues/6748)。历史记录已确认合并。

- 原问题：每周一、三、五 14:30 的任务，从周预设切到 Custom cron 时丢掉星期限制；其他预设也会丢约束。编辑预设后切回自定义，还可能恢复旧表达式。
- 做法：进入自定义编辑器时从当前预设及其字段生成 cron，而不是使用残留的旧值或每日默认值。
- 验证：组件覆盖多种预设和来回切换，真实浏览器覆盖入口及保存请求，并检查只改名称时没有意外重写计划。附桌面和窄屏前后截图。
- 经验：前端也有有价值的业务逻辑 bug，不是只有核心维护者能修。截图展示真实界面，测试再核对最终请求，避免只证明输入框变了。
- 协作：提交后出现同问题的平行 PR；最后由维护者选择合并此 PR。不能把新平行 PR 的出现解释为原贡献必定失效。

## #6687：并发首次上传及安全边界

链接：[bytedance/deer-flow#6687](https://github.com/bytedance/deer-flow/pull/6687)。2026-10-13 的记录显示已关闭、未直接合并，部分工作被维护者移植到 #6632。不要把它写成自己的 merged PR。

- 原问题：两个调用同时看到目标文件尚不存在，都选择相同名字，之后写入互相覆盖；转换后的 Markdown 伴随文件也有相似风险。
- 最初方案：写入临时文件，使用不覆盖目标的原子发布，冲突时重新分配名字；保留约定中的顺序替换行为。
- 评审发现：临时路径能被替换为符号链接，发布可能跟随链接；复制完成并不意味着链接那一刻仍是原文件。清理失败也可能掩盖主操作结果。
- 后续处理：核验打开文件与路径的身份、使用支持的平台 no-follow 能力、验证发布目标、补真实替换与清理测试，并说明不支持能力时的残余限制。未把 macOS 测试说成原生 Windows 验证。
- 经验：不要把这一历史实现当成通用安全文件发布配方。竞态与安全边界需要完整分析，机械套用“临时文件 + 原子操作”不够；部分被采用与原 PR 合并是不同贡献事实。

## Karakeep #3144：解码要追踪完整来源

链接：[karakeep-app/karakeep#3144](https://github.com/karakeep-app/karakeep/pull/3144)。这里只总结会话截图中的评审，不断言当前是否已合并。

- 最初想解决元数据中的 HTML 实体残留，但在汇总层解码会再次处理上游已经解码过的内容，也会在重试时改动已保存文本。
- 机器人提出重复解码、失败抓取早写入及测试绕过真实上游的问题，这些都需要检查实际生产调用链。
- 后续改到采集子进程边界，并保护结构字符；机器人不再提出原先的重复解码问题，但继续提醒 Reddit JSON 路径与原报告范围是否真正对应。
- 经验：bot 的“没发现新问题”不证明原问题已完整解决。仍应验证原始来源、失败/重试路径和用户报告，不能靠给人为编码字符串写测试形成假闭环。

## #6826：报告图片的当前贡献

链接：[bytedance/deer-flow issue #6826](https://github.com/bytedance/deer-flow/issues/6826)。记录时 issue 已由用户创建；不在本复盘猜测后续 PR 编号或状态。

- 原问题：图片能在普通聊天中显示，Markdown 报告预览却把 `/mnt/...` 或相对地址直接交给浏览器，导致报告中缺图。
- 价值依据：仓库自带分析技能确实要求生成本地图表并嵌入 Markdown；不是为了测试虚构一种无来源的报告格式。
- 做法：为共享预览传入文件、会话和 mock 上下文，使用现有 artifact 地址构造；同时处理切换报告时渲染器保留旧地址的问题，保留安全过滤及外链行为。
- 验证：原实现中新回归和实际页面缺图，修复后通过；同版全量前端单测 3161 通过，浏览器套件 427 通过。截图使用真实前端与模拟数据，不宣称真实线上 Agent 或后端部署已验证。
- 经验：过去 #1451 曾被关闭为 superseded，因此必须承认历史工作并证明当前剩余路径，不宣称首次发现。截图中一个 PNG 有两个图表，报告故意用两种路径引用两次，必须说明“四张图”来自夹具而非产品重复渲染。

## 没有提交也是正确结果

**SkillScan #6381 候选**：已经做过修复和测试，最后查重发现 #6428 覆盖同一问题且更全面，于是停止重复提交。早期全量通过不能冒充后来被中断的新基线检查通过。

**到期 cron 更新候选**：可以复现重存任务时改变到期点，但产品语义和实际影响没有建立到足够程度。用户要求撤回，未发布表单已丢弃，本地代码保留。不能把撤回写成“已证明绝不是 bug”，也不能为了挽回投入偷偷重提。

## 共同方法

成功贡献不是“找一行可疑代码、改掉、提交”。我们逐渐形成的是：确认真实入口和合理预期，查清现有工作，用修复前失败证明缺陷，用修复后通过与边界测试证明修复，再把证据、限制和作者责任准确交给维护者。

合并只是协作结果之一。严谨地跳过重复修复、接受正确评审、撤回价值不足的候选，同样是这套流程必须保留的部分。
